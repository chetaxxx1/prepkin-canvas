## Q1. The button rule in dark mode

**Evidence.** `extension/receipt.test.js` L325-332 (`'no rule in the skin writes any property on a button'`): regex `buttonish` over every non-`ours()` selector, but **`if (sel.includes('*') || ... ) continue;`** — any selector containing `*` is skipped entirely. `extension/skin.css` already has ~20 `[class*="..."]` attribute-substring selectors (L150-151, 564-590 etc.) — this is the codebase's standard, forced answer to the *other* house rule ("never a `css-` selector," since InstUI hashes its classnames). `test/pages.test.js` L76-79 `KNOWN`: two accepted-broken spots, `syllabus-dark td.dates > … > button` and `calendar-dark button.navigate_(prev|next)`. `receipt.test.js` L379-384 + `killReason`: `isQuizTake('/courses/4/quizzes/12/take')` turns the **whole skin** off, not just buttons.

**The obvious answer is (b): allow one dark-only, `color`-only rule on backgroundless buttons.** It does not survive unexamined, for a reason nobody asked about: **the rule is not actually blanket today.** `[class*="baseButton"]` — the exact selector shape option (b) proposes — already contains `*`, so it already passes the current test with zero change to `receipt.test.js`. Someone could ship the carve-out in `skin.css` alone, this week, and the suite stays green. That's worse than "relax the rule": it's an *undocumented* hole a future reviewer won't know is sanctioned, sitting next to twenty other wildcard rules that exist for an unrelated reason (InstUI hash-proofing). The real question isn't "relax or hold" — it's "the hole exists; do we close it, name it, or ignore it."

Second correction: the brief frames the risk as "does this break R18 (the quiz kill switch)." It structurally cannot — `isQuizTake` disables `pk-on` (the whole stylesheet) during `/take`, so no button-color rule, present or absent, is live during a quiz. The quiz-safety promise does not depend on this decision at all. The real cost of relaxing is on everyday pages (syllabus, calendar, kebabs) where the skin stays on — a smaller, more defensible blast radius than the brief implies, but also means "protects quiz safety" is not a reason to hold the line; it was never at risk.

**Recommendation, one sentence:** Close the `*` loophole in the test for exactly button-ish attribute selectors, then add one named, explicit exception — `color` only, `dark` scope only, selector list literal (not pattern-matched) — so the permission is visible in the diff instead of inherited by accident.

**Shape:** `skin.css` gets a new, small block: `html.pk-on.pk-dark .btn.btn-link, html.pk-on.pk-dark [class$="baseButton"][class*="color-secondary"] { color: inherit; }` (exact InstUI classnames need confirming on the sandbox — did not check the live markup for the syllabus/calendar buttons' real class names, only their selector shape in `KNOWN`). The test changes: the `*`-skip becomes conditional on `ours(sel)` only, and a second, explicit allowlist (`ALLOWED_BUTTON_COLOR`) is checked against instead of blanket-exempted. `KNOWN` in `pages.test.js` shrinks by two once the fix lands; if it doesn't, that's the test catching a fix that didn't work.

**Confidence: medium.** High confidence on the loophole and the quiz-safety decoupling (both read directly off the test file). Medium on the exact selector to add — did not check the live sandbox markup for the two `KNOWN` buttons' actual classnames.

## Q2. Tick a row done (A1)

**Evidence.** `ios/Sources/Core/GameState.swift` L835-843 `applyDoneMarks`: pays a `DoneMark` only if `tasks.first(where: {$0.id == mark.taskID})` exists on **today's list** and `!task.done` — `complete(taskID:reward:)` runs the same ledger-key dedupe as a real hand-in. `ios/Shared/DoneMarks.swift` L3-9: "Neither of those processes may pay coins... the tap leaves a mark here... the app reads the marks on its next open, pays each one once." This is the widget/notification precedent the brief points to, confirmed: **it already pays a Canvas-style task without Canvas proof, same reward.** `extension/background.js` L284: `queueRequest({ kind: 'focus', taskId: focus.taskId, minutes: focus.durationMin })` — a **second**, independent precedent: the extension already asks the phone to pay coins for something proven only in the browser (a timed focus session), via the same `requests` queue described at L460-476.
`extension/content.js` L92 `COIN_REWARD = 30` (display only). `ios/Sources/Core/Content.swift` L103 `let reward: Int` — per-task, not a constant; 30 is GameState's number for a Canvas/dated task, not a hard rule everywhere.
Own-task done handler, L2253-2256: sets `submittedAt` locally and writes `chrome.storage.local` — **nothing else.** L2519-2523: `data = composeData(stored.lastPayload, ownTasks, nicknames)` — `ownTasks` never leave the laptop; `background.js`'s `send()` only reads `lastResults` (Canvas-sourced) and `requests`. Today, ticking an own-task pays nothing.

**So the "obvious answer" — one circle, everywhere, pays 30 coins like a hand-in — has a real hole the brief doesn't name.** `ownTasks` are entirely self-reported: title, date, course, all typed by the student, zero Canvas validation (`content.js` L2260-2270, the add-task submit handler). If ticking pays coins uniformly across all row types, a student can add unlimited fake own-tasks and mint unlimited coins — a cheat surface that **does not exist in the app today** (own-tasks currently pay nothing), so "tick a row" would be the feature that creates it, not just inherit it. The two precedents the brief cites (DoneMarks, focus requests) both have a real cost gate the naive design would drop: DoneMarks only pays tasks that are already on today's Canvas-or-dated list (can't fabricate the task), and a focus request costs real minutes. A tick with no such gate is a third, weaker case.

**Is a tick BLOAT or the core of the to-do list, by the students' own words?** `FEATURES-STUDENTS.md` #15 "Better to-do list" is **LOVED, 16 people / 131 upvotes**, the single largest to-do number in the grid — and the quoted evidence is about *visibility* ("everything due... rather than navigate every course"), not the tick mechanic specifically. `research-bettercampus-likes.md` §4 "Visible completion — the progress ring" is the closest match to "a tick," and it's listed fourth of seven loved things, weaker than dark mode, themes, and the unified list itself. Nowhere in either source does a student single out "the checkbox" as the loved gesture — the brief's framing ("the single most-used gesture") is VERDICT's own characterization (A1), not a sourced student quote. That doesn't make it wrong, but it should be labeled as inference, not evidence.

**Recommendation:** Ship the circle only on **Canvas-sourced and dated tasks** (the same population `applyDoneMarks` already trusts), not on own-tasks, at first. Reward = 30, gated the same way DoneMarks gates it (today's list only, one ledger key, `pay()`'s existing dedupe). Own-tasks keep their current local-only tick (no coins) until a real rate limit or a Canvas-verification pass exists for them — this is a scope cut, not a redesign, since the wiring (`ownTasks`, `composeData`, storage) is already there and untouched by this change.
**Shape:** one circle per due row (rail, card's one line, planner rows, side panel); tapping writes `{taskId, at}` to a `chrome.storage.local` done-set and queues a `DoneMark`-shaped request over the existing `requests` bridge (L595-606); the phone runs it through `applyDoneMarks` unmodified. Test: a unit test asserting the extension never queues a done-request for a task whose id starts with `own-` (the id prefix `content.js` L2269 already uses), plus a GameState test that a repeated `DoneMark` for the same task pays once (this likely already exists — did not check `GameStateTests`).
**Confidence: medium.** High on the mechanism and the cheat-surface gap. Medium on "should own-tasks ever pay" — that's a product call, not a code fact.

## Q3. Looks tiles as real renders (D1/A4)

**Evidence.** `extension/receipt.js` L15-40 `PAPERS`: a closed catalog of paper tokens (ink/rule/mark/paper/paper2), already AAA-measured. L210-232 `themeStyle(look, textureImage, art)`: generates a scoped `<style>` block, `html.pk-on.pk-theme-<id>{--pk-mark:…;--pk-rail-image:…;--pk-wallpaper:…;--pk-card-art-N:…}` per theme, **already looping all themes × light/dark** — this is the exact token surface a tile needs, built and in production for the live theme, not new infrastructure. `extension/planner.js` L422-475 `renderLooks()`: already loops `LOOKS`/`LOOKS_BY_ID` from `plannerLooks()`, already data-driven, already renders locked/owned/price state. `FEATURES-STUDENTS.md` #3 **"Community theme marketplace (browse/like/comment)" — LOVED, 22/97**, vs. #6 **"Save a custom theme (Pro-gated)" — HATED, 18/90**, and the quote for #6 is about losing *saved custom CSS themes*, not about browsing a gallery.

**The brief's own framing conflates two different rival features, and that changes the risk math.** "The rebuilt theme editor drew 18/90 against" (#6, saving/editing your own theme) is not the same feature as "26 curated themes as real-render tiles" (closer to #3, browsing pre-made themes, which is the #1 most-loved row in the whole grid). We are not building an editor and not asking students to save custom CSS — VERDICT §3 REFUSE explicitly rules out "a theme marketplace" and "AI anything." So the risk the brief worries about (the editor's 18/90) sits on a feature we've already refused to build, not on this one. The real comparable is #3's 22/97, which is unambiguously positive and about exactly this: seeing the theme before committing.

**Options.** (a) CSS mini-page from tokens, scaled: cheapest, reuses `themeStyle()` + `PAPERS` + `LOOKS` wholesale, zero network, deterministic, testable (assert a tile's computed `--pk-mark` equals the theme's accent). (b) shadow-root DOM clone of the live dashboard, scaled: heavier (26 clones of real Canvas markup, InstUI hash-fragile, hard to keep under the 2s mount budget), but "this student's actual dashboard" more literally. (c) offscreen iframe per theme: violates "zero network" in spirit even without a real request (26 same-origin iframes are real DOM/paint cost) and is the heaviest to keep inside the mount-time budget in `test/pages.test.js`. (d) pre-rendered static images: cheapest to render, but not *this student's* cards/colours — fails the brief's own bar ("two of their cards in their Canvas colours").

**Edge cases.** A student with zero courses or all-grey Canvas colours makes every tile look the same regardless of approach — worth a design fallback, not a blocker. Wallpaper themes (image themes, `art/` bundled) need the `art.wallpaper`/`art.cards` tokens `themeStyle` already handles — no new asset pipeline. 26 live-scaled mini-pages is more DOM than the current tab; the 2s mount-time allowance in `pages.test.js` is measured skin-on-vs-off on a real page, and a Looks-tab-open state may need its own budget line, since the existing measurement isn't scoped to that tab specifically.

**Recommendation, one sentence:** Build (a) — a CSS mini-page per tile driven by the same `PAPERS`/`themeStyle()`/`LOOKS` data already shipping, not a DOM clone or iframe, because the token surface already exists and a fabricated two-card mini-layout is cheaper and more stable than cloning real, hash-fragile Canvas markup. **Shape:** a small fixed markup skeleton (rail sliver + two card shells, no real assignment text) styled by injecting the theme's token block and the surrounding tile at `transform: scale()`; worn = one ticked; locked = price shown. Test: `assert.equal(getComputedStyle(tile).getPropertyValue('--pk-mark'), LOOKS_BY_ID[id].accent[mode])` per theme, plus a `pages.test.js` mount-time check scoped to the Looks tab open.
**Confidence: medium.** High that (a) is architecturally cheapest given what's already built; did not measure actual render cost of 26 tiles, so "worth ~a day" in the brief is unverified, not confirmed.

## Q5. Order and cuts

**Evidence.** VERDICT §6 (order 1-10, `design/canvas-skin/VERDICT-2026-09-14.md` L229-248) and §3 REFUSE (L165-172). `extension/manifest.json` (full file read). `FEATURES-STUDENTS.md` §Firefox row (#100 doesn't cover it; the Firefox/Edge gap is covered qualitatively, not as a numbered feature). `research-bettercampus-likes.md` L198 "Firefox / Edge support | 9 | 9 | 20 | 5" and L285 "Firefox and Edge are an unserved gap — 9 people." VERDICT L24 "Firefox | Abandoned: last build Oct 2024, 33K users." Design specs: `design/canvas-skin/SPEC-LOW-BEAM.md` L253/269/514, `SPEC-MEASURE.md` L223/240/516, `RESEARCH.md` L91/160/168/186/379/465 — all independently state **768px is Canvas's own responsive breakpoint** (Canvas's global nav collapses to `#mobile-header` below it), not a number chosen from any student-usage data.

**Is 4→10 the right order for one person / ~25 hours?** Partial no. Steps 4 (tick) and 5 (Planner, which folds in X2/X5/X7 and the three orphaned-door fixes) are correctly first — they're the features VERDICT itself says "a switching student would miss," and Q4's dead-view finding shows step 5 is more delicate than "delete 600 lines," which argues for doing it early while the person who found the duplication (this pass) is fresh context, not late. Step 6 (Looks tiles) is well-motivated by the evidence (#3 is the single most-loved row, 22/97) and, per Q3, is cheaper than the brief assumes because the token infrastructure (`themeStyle`, `PAPERS`) already exists — I'd pull it to **before** step 5, not after, since it's likely a half-day given (a), and shipping the #1-loved surface earlier de-risks the release if time runs out. Step 8 (per-page pass at 1280 **and** 768) is the one I'd cut in scope, not order: I found zero evidence — repo-wide grep, not web search — that 768 is a measured student width; it is Canvas's own CSS breakpoint (four independent spec docs, all `display:none` cutovers), which is a legitimate reason to test it (a real layout mode Canvas ships) but not the reason the brief implies (a common student window size). Testing it is still cheap once `pages.test.js`'s harness exists, so I wouldn't drop it — I'd just stop calling it "students run Canvas at 768" in any external copy, because that specific claim is unverified.

**What I'd cut outright:** X8 (Recent Feedback, "fold it to one line") is scoped as part of step 2 (card) already landed per §7 — confirm it's actually done before counting it in 4-10's remaining budget; did not re-verify against the current card markup. Step 9 ("Words": no uppercase, no "receipt," counts once) is mechanical and can be **merged into whichever step touches each surface** rather than held as its own pass — R1/R4/R6 fixes are one-line CSS/copy edits per surface (VERDICT already did this for the rail and card in steps 2-3); a dedicated ninth step for words the rail and card already fixed is doing per-surface work twice. Merge it into 5, 6, 7 as each surface is touched.

**Firefox (A7), facts not guesses, checked against `extension/manifest.json`:**
- `"side_panel": {"default_path": "sidepanel.html"}` + the `"sidePanel"` permission: **confirmed break.** Firefox has no `chrome.sidePanel`/`side_panel` equivalent; it uses `sidebar_action`/`sidebarAction`, a different, per-window (not per-tab) API (MDN "Chrome incompatibilities," checked live). This is a real UI rewrite for the side panel specifically, not packaging.
- `"background": {"service_worker": "background.js"}` with no `scripts` key: **confirmed break, small fix.** Per MDN's background-key docs (checked live), Firefox does not start a background context from `service_worker` alone — it needs `scripts: [...]` listed alongside it (both keys, cross-browser pattern). One line, not a rewrite.
- `chrome.*` namespace (`chrome.storage`, `chrome.alarms`, `chrome.scripting`, `chrome.action`, used throughout `background.js`/`content.js`): Firefox has supported a `chrome.*` compatibility alias for years. Whether that alias returns Promises when called with no callback the way this code assumes (`await chrome.storage.local.get(...)`, used pervasively — e.g. `background.js` L466, L594) — **did not verify.** If it doesn't, every awaited `chrome.*` call needs a callback-to-Promise wrap, which is not "packaging," it's a real port.
- `"use_dynamic_url": true` on `web_accessible_resources`: **confirmed non-issue.** Checked live (Bugzilla + MDN): Firefox does not implement the flag but also does not error on it — it's silently ignored, and Firefox already randomizes its extension UUID per-install for the same anti-fingerprinting reason, so the omission costs nothing.

So "Firefox is packaging" (VERDICT A7) is **half right, checked**: the manifest-only fixes (`scripts` key, dropping/ignoring `use_dynamic_url`) are packaging. The side-panel rewrite is not, and the `chrome.*` promise question is a real unknown that could turn A7 into a multi-day port rather than a CI job if it goes the wrong way. I'd keep Firefox last as VERDICT says, but flag it to George as "packaging, with one open question that could change the estimate" rather than a flat "packaging."

**Recommendation, one sentence:** Keep 4-and-5 first, pull 6 (Looks tiles) ahead of 7 given its lower-than-assumed cost and highest-loved evidence, fold step 9 into whichever surface step touches each rule instead of a standalone pass, and re-scope step 8's "768" language to "Canvas's own mobile breakpoint" rather than a student-usage claim since no usage evidence exists in this repo.

**Confidence: medium-high** on the Firefox facts (three checked live against MDN/Bugzilla, one explicitly flagged unverified). **Medium** on the reordering — it's a reasonable read of the same evidence VERDICT had, not new data, except for the Q3/Q4 findings that inform it.
